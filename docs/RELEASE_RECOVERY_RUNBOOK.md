# RentManor release, recovery and operator procedures

This runbook is executable preparation, not evidence of a live backup or monitoring service. No production migration or replacement was performed in the remediation assignment.

## Isolated verification

Use Node 22 or newer. Run `npm ci`, `npm test`, `npx playwright install chromium webkit`, then `npm run test:browser`. The browser harness serves a null backend configuration and blocks every remote request. Optional RENTMANOR_CHROMIUM and RENTMANOR_WEBKIT environment variables select already-installed browser executables. SQL tests use a new PGlite database per scenario, synthetic users and SQL stand-ins for Auth/Storage. They exercise PostgreSQL constraints/RLS/functions, not the Supabase provider's HTTP/Auth/Storage implementation or real concurrent connections.

Before release, additionally use disposable local Supabase (Docker + Supabase CLI) or an explicitly authorized free disposable project. Confirm its project reference is different from production. Configure email capture, not real recipients. Repeat signup confirmation, wrong-email metadata, explicit/automatic invite acceptance, expired/revoked/reused/competing tokens, member/nonmember/anonymous direct requests, storage size/type/overwrite/delete denials, upload and cleanup failures, account switching/removal/reload, and every seven-table/binary recovery phase. Test concurrent requests through separate sessions. Record targets, counts and results without passwords/tokens/tenant data. This infrastructure was unavailable here; do not substitute production.

## Schema installation and upgrade order

* New disposable installation: apply `supabase/schema.sql` once. It includes the complete forward remediation. Do not run a historical migration afterward.
* Existing audited/tabs-enabled schema: preflight and backups, then `20261007_complete_remediation.sql` in one transaction. Repeat application is tested and non-destructive with compatible data.
* Older pre-tabs schema: after read-only review and a disposable rehearsal, apply `20260919_photos_expenses_sample.sql`, then **20261007_tabs_upgrade_bridge.sql**, preflight, and `20261007_complete_remediation.sql`. Skip the old `20260919_property_tenant_tabs.sql` in this route: its sample seeding collides with thumbnail/contact backfills. The forward bridge preserves those backfills, tolerates preexisting sample photo/tenant uniqueness, and resolves correspondence to the actual sample tenant ID. Historical migrations remain unchanged. Never apply the bridge after complete remediation, because it contains historical function definitions that the final migration supersedes.
* `node scripts/sync-schema.mjs` maintains the fresh schema's forward suffix. Review any historical-prefix edit separately. Missing migrations fail visibly; the app does not discard unsupported optional values and pretend a save succeeded.

Legacy short invitation links are revoked by the upgrade. Owners must manually create and share new links. Existing accepted links never become reusable. No messages are sent automatically.

## Configuration and static build

`app/config.js` is the only browser backend configuration; index.html contains no inline production credentials. Production configuration allows the intended production hosts. Localhost additionally requires environment='local' and an explicit localhost allowedHosts entry. Use config.example.js with a disposable target, never paste a privileged key. The committed public anon key is a public identifier whose safety depends on RLS; do not log or include keys in reports. `.env.example` is not loaded by this static app.

`node scripts/build-static.mjs` generates dist/app and dist/site plus root redirect files. Netlify publishes dist. Tests, SQL, ZIPs, tmp exports and node_modules are excluded. Start with a clean generated dist if source files were removed; verify its contents before upload. GitHub Pages remains main/root as the historical fallback; do not put private files in a public repository. No branch was merged during this assignment.

## Full backup and replacement

Account → Backup & restore exports canonical seven-table account records and every referenced thumbnail, gallery image, receipt, lease and correspondence binary. It exports no credentials, sessions, membership rows or invitations. Manifest counts and SHA-256 hashes detect corruption; a second database snapshot rejects concurrent changes. Sensitive archives are ordinary private local files, not encrypted by the app. Store them in an access-controlled encrypted location; no automatic schedule or retention promise exists.

Run `node scripts/verify-backup.mjs <private-archive.json>` offline. It prints counts only. Validate each representative image/PDF in a reader; a correct header/checksum alone does not prove arbitrary files can render. Periodically perform a full restore into an authorized disposable account and re-export. Compare all record fields/relationships (account/path rebinding is expected), counts, primary covers and every binary hash. Also test cancellation, denied upload, missing file, changed snapshot and denied commit. Do not call an archive complete if any file is missing, inaccessible or unsupported.

The restore UI validates and previews the incoming archive, downloads a verified current-account recovery point, and requires REPLACE. Ensure that download actually finished and is retained. Incoming binaries use unique recovery-stage paths, are downloaded and hash-verified before the transactional row replacement. A stale revision aborts. Failed staging/commit attempts compensate only new unreferenced objects; originals remain untouched. Abrupt browser termination may leave unreferenced stages/objects; there is no automatic garbage collector. Keep the recovery point until an operator has verified the restored account.

For rollback, use the before-restore archive through the same complete restore path; it stages and verifies its own files before relational replacement. Do not roll back constraints by deleting data. An older frontend may overwrite referenced objects or invoke an obsolete restore endpoint; use only the compatible release. Schema rollback requires an individually reviewed forward correction or verified operator database-plus-media recovery, not a generic destructive down migration.

Legacy array/object/version-1 imports are property-only merges, preserve existing rows/children, validate supported fields, deduplicate fingerprints, and reject existing-ID conflicts in the UI. Missing entries are never deletion instructions. Attachment contents are not recreated from legacy paths. Similar addresses remain distinct; the old browser source is not cleared.

## Cleanup and account/data deletion

After upload replacement commits, the app attempts to remove the superseded object. SQL Storage policies prohibit removing or overwriting referenced objects; the client also checks references. A failure leaves recoverable bytes and reports partial success. Operators must inventory account-scoped objects against all seven tables and retained recovery points before any cleanup. Prefix alone is insufficient evidence of abandonment. No scheduled or indiscriminate deletion is configured.

For a verified owner account-deletion request, first establish authorization, shared-member impact, retention obligations and whether a recovery point must be retained. These business decisions require the operator's policy. Freeze writes and inventory every object and membership; obtain any approved recovery point and verify it offline. Rehearse with disposable synthetic data. In an explicitly authorized operator transaction, remove that account's recovery_stages rows, then its accounts row (review current cascade FKs first). Commit only after verifying expected scoped row counts and zero impact on other accounts. Remove only the previously inventoried, now-unreferenced Storage objects using the Storage API, not storage.objects SQL. Verify all metadata/object counts and report failures. Do not delete an Auth identity that belongs to other accounts. Auth deletion is a separate authorized action after checking every membership. Supabase platform backups and previously downloaded archives are not erased by account deletion; the operator must define their handling. No public self-service account-deletion feature or established request address exists in the repo.

## Health, mobile and policy limits

The health script checks HTTP availability and served/static hashes without reading customer records. No scheduler, paid monitor, incident delivery channel or automatic backup service was configured. Owner action is needed to choose any cadence/contact and publish approved policies. Privacy/terms remain clearly marked drafts; no support email, retention duration, legal entity or compliance promise was invented.

Private operations require network access. The worker caches the curated public shell/local sample only, ignores configuration, API traffic and signed files, and replaces v23 with v24. Local sample startup with no backend/CDN, Chromium cache upgrade/offline/reconnect, mobile-width Chromium/WebKit and keyboard tabs were exercised. Physical iPhone camera/HEIC conversion, Safari installation, device sharing, native contact handlers and full private-account accessibility remain unverified. Unsupported HEIC/HEIF must be converted to JPEG when the browser cannot decode it. Embedded Noto Sans PDF reports preserve supported Latin/Greek/Cyrillic text and paginate long text; unsupported scripts/emoji produce an actionable CSV alternative. CSV neutralization prepends an apostrophe to formula-leading user text including whitespace/control prefixes.
